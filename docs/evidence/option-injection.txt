Option-injection through "setenv opt" — OpenVPN 2.6.14, 2026-11-14
=============================================================

Engine under test
  C:\Program Files\OpenVPN\bin\openvpn.exe
  (same binary the app launches; Authenticode-verified by the app)

Why this matters
  OpenVPN parses "setenv opt <option>" as if <option> were written as a
  normal directive. A profile could therefore hide a plugin/script hook
  behind a directive name the sanitizer did not recognise.

1. Hostile profile, run directly by the engine
   File contents (profile body; CA supplied on the command line):
     client
     dev null
     remote 127.0.0.1 1
     verb 4
     setenv opt plugin "<temp>/evil.dll"

   Command:
     openvpn.exe --config hostile.ovpn --ca <fixture cert> --connect-retry-max 0

   Observed output:
     == hostile exit=1 ms=44
       2026-11-14 02:00:29 us=640000 PLUGIN_INIT: could not load plugin DLL: C:\Users\DELL\AppData\Local\Temp\aivpn-inj-c13t2S\evil.dll. The DLL is not in a trusted directory.
       2026-11-14 02:00:29 us=640000 Exiting due to fatal error

   Reading: the engine reached PLUGIN_INIT, i.e. the directive hidden behind
   "setenv opt" was executed as a real option. The only thing that stopped
   the load was OpenVPN's own "trusted directory" restriction on plugin
   paths. Without the sanitizer there is no second layer.

2. Same profile after the app's sanitizer
   sanitizeConfig() output (every line prefixed with two spaces for this dump):
     client
     dev null
     remote 127.0.0.1 1
     verb 4

   Command: identical, only the config file differs.

   Observed output:
     == sanitized exit=1 ms=36
       Options error: No client-side authentication method is specified.  You must use either --cert/--key, --pkcs12, or --auth-user-pass

   Reading: the plugin line is gone before the file is written; the engine
   never sees a plugin option and stops at the auth-method check instead.
   (The real app supplies auth-user-pass / the profile's own credentials.)

3. Leading "--" prefix — second bypass, found 2026-11-14
   OpenVPN's config parser strips a leading "--" before matching the option
   name, so "--plugin" runs the same code as "plugin". The first sanitizer
   version matched only the bare name and let this through.

   Profile body:
     client
     dev null
     remote 127.0.0.1 1
     verb 4
     --plugin "<temp>/evil.dll"

   Observed, run directly by the engine:
     == hostile exit=1
       2026-11-14 02:06:39 us=62000 PLUGIN_INIT: could not load plugin DLL: C:\Users\DELL\AppData\Local\Temp\aivpn-dashdash-GzJf6S\evil.dll. The DLL is not in a trusted directory.
       2026-11-14 02:06:39 us=62000 Exiting due to fatal error

   Same file after sanitizeConfig (lines prefixed for this dump):
     client
     dev null
     remote 127.0.0.1 1
     verb 4

   Observed:
     == sanitized exit=1
       Options error: No client-side authentication method is specified.  You must use either --cert/--key, --pkcs12, or --auth-user-pass

   The sanitizer now strips one leading "--" before matching, the same
   normalization the engine applies, so "--plugin", "--up", "--management"
   and "--script-security" are removed. A benign "--remote ..." is kept.

   Other spellings tested against the same engine and found not executable:
     setenv safe-opt plugin ...   -> Options error: Unrecognized option: setenv
     setenv opt "plugin <path>"   -> Options error: Unrecognized option: plugin <path>
     setenv opt --plugin ...      -> Options error: Unrecognized option: --plugin
     plugin="<path>"              -> Options error: Unrecognized option: plugin=<path>
   Tab separators ("setenv<TAB>opt<TAB>plugin") do reach PLUGIN_INIT in the
   engine, and the sanitizer already removes them because "\s" matches tabs.

4. Unit coverage
   scripts/unit-tests.js asserts:
   - "setenv opt plugin ..." and "SETENV   OPT   up ..." are removed,
   - "setenv OPT script-security 2" and "setenv opt tls-crypt-v2-verify ..."
     are removed,
   - a plain "tls-crypt-v2-verify ..." line is removed,
   - "--plugin", "  --up" and "--script-security 3" are removed while
     "--remote host 1194" survives,
   - a benign "setenv FOO bar" survives,
   - buildConfig always emits exactly one "script-security 1".

Limits of this evidence
   This proves option-level behaviour of the engine and of the sanitizer.
   It is not a tunnel test: no server was contacted, no adapter was opened,
   and no elevation was involved. Live UAC tunnel verification remains
   pending and is not claimed here.
