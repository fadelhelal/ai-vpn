Management socket owner verification — 2026-11-13, Windows 10.0.26300
=====================================================================

What ran: src/mgmtpeer.js (the production module) against a live loopback
socket accepted by the current process. The current process stands in for the
engine so the test can run without elevation; in production the expected owner
is the elevated openvpn.exe pid read from engine.pid.

--------
port=63099 owners=[31572] currentPid=31572
netstat line (first match): TCP  127.0.0.1:63099  0.0.0.0:0  LISTENING  31572
executable=C:\Program Files\nodejs\node.exe

verify with this process as engine:
  {"ok":true,"reason":null,"pid":31572}
verify with a different engine path:
  {"ok":false,"reason":"path-mismatch"}
verify with a foreign pid:
  {"ok":false,"reason":"pid-mismatch"}

Notes
-----
- Owner detection uses ESTABLISHED rows of `netstat -ano -p tcp` for
  127.0.0.1:<port>; the executable path comes from Win32_Process through CIM.
- The password and all management commands are sent only after this verdict is
  ok, so a process that binds the port first gets no secret and cannot forge
  tunnel state through the app.
- Not covered: a live run against the real elevated engine pid (requires an
  interactive UAC tunnel). The lookup path itself is exercised here.
- Residual: the pid file and TCP table are visible to the same user. An attacker
  who starts a process whose executable path is the engine binary would pass the
  path check, but an unelevated engine cannot form a tunnel, so it cannot
  produce a real CONNECTED state.
