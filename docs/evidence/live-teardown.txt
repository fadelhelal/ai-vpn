Live teardown on a real tunnel — 2026-11-14, Windows 10.0.26300
===============================================================

What ran: the production VpnSession code path (src/session.js, src/elevate.js)
inside Electron on the real device, with the installed OpenVPN 2.6.14 engine
and a real relay server. The UAC prompt was shown and accepted by the user.
The script connected, waited for the tunnel, then forced a failure
(session.fail('tls')) to test the exact path that leaked an engine in 0.2.13.

Defect found live (fixed in the same version)
---------------------------------------------
The UI reported FAILED (error "route", detail ENGINE_TIMEOUT) during the same
run while the engine log proves the tunnel was up. Two UI-layer causes:

1. The management password verdict was never seen. OpenVPN's "ENTER PASSWORD:"
   prompt has no trailing newline, so the verdict arrives glued to it in one
   chunk ("ENTER PASSWORD:SUCCESS: password is correct\r\n>HOLD:..."). The
   line-anchored match on "SUCCESS: ..." never fired, the handshake timed out,
   and every retry burned the deadline until ENGINE_TIMEOUT. Captured raw
   response from a local probe of the real engine:
   "ENTER PASSWORD:SUCCESS: password is correct\r\n>HOLD:Waiting for hold release:0\r\n"
2. While classifying the failure, the log pattern "route add" also matched the
   benign line "Route addition via ipapi [adaptive] failed because route
   exists", producing the wrong "route" error.

Fixes: the handshake verdict is now matched on the raw buffer (and unit-tested
against the exact captured bytes, including a verdict split across chunks);
the route pattern now only matches real failure lines ("route addition failed",
"route add command failed", add_route) and never the benign route-exists line.

What this run proves
--------------------
- The elevated supervisor works on a real elevated engine: a forced failure
  after a genuinely connected tunnel left no live engine, no tunnel routes,
  no changed exit IP, and no leftover firewall state.
- Route cleanup ran against the pre-launch snapshot: nothing to remove after
  teardown, and the two split-default routes the engine had added are gone.

Limits
------
- Run once; no long-duration stability claim.
- The in-app route snapshot "while connected" came up empty because the test
  script took it after fail() had already torn the tunnel down; the engine log
  plus the zero-split-defaults-after figure are the evidence that the routes
  existed and were removed.
- The UI-layer handshake fix is verified by unit tests on the exact captured
  bytes, not yet by a second live elevated run (that would cut the network
  again and needs the user's consent).
- The old supervisor script captured in engine-supervisor.txt was hardened the
  same day (identity-checked stop, engineStopped/exit 5, snapshot guard); see
  the addendum there.
