Kill switch tunnel allowance — 2026-11-14, Windows 10.0.26300
=============================================================

What was tested: packaged AIVPN 0.2.14 (rebuilt with the fix), real UI driven
over the Chrome DevTools protocol, real OpenVPN 2.6.14 engine, real private
profile (Stockholm relay), kill switch enabled with strict = true (saved
settings). UAC was approved once for the connection. The connected capture ran
from a normal user PowerShell (not elevated), so it measured what any app sees.

Defect observed before the fix (same host, same relay)
------------------------------------------------------
- UI state CONNECTED, engine and supervisor alive.
- Routes 0.0.0.0/1 and 128.0.0.0/1 via 10.8.0.1 on ifIndex 17
  ("OpenVPN Data Channel Offload", Status Up, address 10.8.0.2).
- Get-NetConnectionProfile reported the adapter as NetworkCategory = 0 (Public),
  IPv4Connectivity = 1.
- Firewall profiles Domain/Private/Public: DefaultOutboundAction = 4 (Block).
- Only two rules existed: engine -> relay transport, and
  "VPN interface" with InterfaceType = 4 (RemoteAccess).
- Find-NetRoute for 1.1.1.1 selected the DCO adapter, and HTTP to
  http://api.ipify.org failed with "Unable to connect to the remote server"
  while DNS resolution still worked. So every application packet went out the
  DCO interface and was dropped by the default block: the internet died as soon
  as the tunnel connected.

Fix
---
The watchdog now enumerates adapters whose InterfaceDescription matches
OpenVPN|Wintun|TAP-Windows and creates an outbound allow rule per interface
name, named "AI VPN Kill Switch tunnel <name>". The adapter is created only
after the engine connects, so the rule is added from inside the watchdog loop
(re-checked every 500 ms) instead of once at start. Names containing the
wildcard characters * ? [ ] are skipped so a rule can never widen to every
adapter. Rules stay under the same prefix, so the existing clean-stop and
recovery paths remove them together with the other kill switch rules.

Limits
------
- One live run of the fixed build. It proves tunnel traffic passes with the
  default block active and that teardown restores the host; it says nothing
  about multi-hour stability.
- The browsing checks used HTTPS GETs from PowerShell, not a rendered browser.
  The UI itself was driven over CDP for connect/disconnect, not clicked by hand.
- Sites that geo-block Iraq were not individually tested; the evidence is that
  all traffic exited from the Stockholm relay.
- The capture JSON files are stored next to this file exactly as written on the
  host: killswitch-tunnel-connected.json and killswitch-tunnel-after.json.

Blocked-site attempt — same day, separate short run
---------------------------------------------------
Two independent Iraqi outlets are reported blocked by Freedom House (Freedom on
the Net 2024): Ultra Iraq (blocked November 2023) and Al-Hudood (blocked
February 2024). Both were tried by name from this host (Iraq) before connecting,
through the tunnel with the kill switch active, and after disconnecting.

Before connecting:
  ultrairaq.ultrasawt.com  DNS failed locally: "The remote name could not be
      resolved". A public DoH query (Cloudflare) returned 5.178.43.113 and
      5.178.43.96, so the name exists and the local resolver filters it.
  alhudood.net             HTTP 200 from this line (not blocked here today).

Through the tunnel (Chrome headless, desktop user agent):
  ultrairaq.ultrasawt.com  DNS now resolved (23.215.2.9, Akamai) and the CDN
      answered 403 "Access Denied" for the relay address. So the local DNS
      block is bypassed, but this site's CDN refuses the datacenter IP.
  alhudood.net             HTTP 200, page rendered (title and homepage cards
      visible in the screenshot, dated 14 November 2026).
  www.google.com           HTTP 200 in the same run.

After disconnecting:
  ultrairaq.ultrasawt.com  DNS fails again locally, as before connecting.
  alhudood.net             HTTP 200.
  Kill switch rules remaining: 0.

What this shows and does not show: the tunnel removes the local name-resolution
block, but a site behind a CDN can still refuse the relay's datacenter address
with 403. That is a server-side decision, not a client failure, and it is not
something the app can fix.
